## Architecture

This is a marketing/SEO site for a Perth garage-door business. Almost every page is **data-driven** — from local TypeScript content by default, or from the **live CMS** where its cutover flags are on (see **CMS** below) — rendered through a small set of reusable template components. Public pages are statically generated at build time (`generateStaticParams` + `dynamicParams = false`) with ISR revalidation; there is no per-request fetching for them (the CMS, when enabled, is read at build/revalidate, not per request). The `/admin/*` CMS dashboard is the exception — it is dynamic/server-rendered.

### The content pipeline (the core pattern)

Each page *type* flows through four layers — to add or change content you usually touch only the first:

1. **`content/<type>/...`** — the content store. Two shapes exist, both ending in a **registry** that exports an array:
   - **Directory-per-type** (one file per instance): `content/<type>/<slug>.ts` is a plain typed object; the sibling `content/<type>/index.ts` imports each instance and exports them as an array. Used by the larger page types — `articles`, `case-studies`, `comparison-pages`, `cost-guides`, `landing-pages`, `service-pages`.
   - **Single-file registry**: a flat `content/<type>.ts` exporting the array directly. Used for the smaller/list-style datasets — `services.ts`, `problems.ts`, `reviews.ts`, `testimonials.ts`, `gallery.ts`, `service-areas.ts`, `service-area-regions.ts`, `service-suburb-pages.ts`, `blog.ts`.
   - Ship a new page by adding the entry (and pushing onto the registry array) — no routing or component changes.
2. **`lib/data/<type>.ts`** — an `async` data-access layer (`get…BySlug`, `get…Slugs`, `get…`) wrapping the registry. There is one per content type (see `lib/data/` for the full list). **All call sites (routes, templates, sitemap) go through this layer, never the `content/` registries directly.** It is deliberately async so the backing store swaps from local files to the CMS API without changing call sites — a cutover that is **now live** behind per-type flags (see **CMS** below; original design in `docs/cms-architecture.md`).
3. **`types/<type>.ts`** — the interface shared by the content file, the data layer, and the template. `types/index.ts` holds the cross-cutting ones (`FAQ`, `Service`, `Problem`, `ServiceArea`, `BreadcrumbItem`).
4. **`components/.../<type>-page-template.tsx`** — the `…PageTemplate` component that consumes one typed object and renders the page from composable section components in `components/sections/<type>/` (or `components/page/` for the service-suburb template).

### Routing

Most routes are thin: resolve slug → call the data layer → render the template, plus `generateMetadata` using `buildMetadata`.

- **`app/[slug]/page.tsx` is shared by four "flat" page types** — service, comparison, cost-guide, and service-suburb pages all live in one top-level slug namespace and are resolved by trying each registry in turn (in that order; the first match wins, so slugs must be unique across all four). `generateMetadata` and the default export each walk the same chain. **Never add a sibling `app/[other]/page.tsx`** — Next.js rejects two differently-named dynamic segments at the same path level (ambiguous-route build error). Add a new flat type by extending this file's resolution chain *and* its `generateStaticParams` `Set`.
- Other types have their own namespaced dynamic routes: `app/blog/[slug]`, `app/case-studies/[slug]`, `app/problems/[slug]`, `app/lp/[slug]`.
- `app/lp/*` are **paid landing pages**: conversion-first, `noindex`, never linked in-site, and they use their own minimal chrome from `app/lp/layout.tsx`.
- **Static listing / standalone pages** (their own folder, no dynamic segment): `app/page.tsx` (home), and the index pages `app/services`, `app/service-areas`, `app/cost-guides`, `app/blog`, `app/case-studies`, `app/problems`, `app/reviews`, `app/gallery`. Plus standalone pages `app/about`, `app/contact`, `app/calculator`, `app/privacy`, `app/terms`, `app/warranty`, `app/warranty-registration`, and `app/garage-door-motors-perth` (branded Capital 1100N/1500N motor product page — sections in `components/sections/motors/` with a shared `motor-data.ts`; imagery lives on the Bunny CDN under `capital-garage-door/motors/`, re-uploadable via `npx tsx scripts/upload-motor-images.ts`; the slug is reserved — a CMS page published under it would be shadowed by this route). These pull lists from the data layer but aren't part of the slug-resolution chain. `app/service-areas` is a single listing page (regions + suburbs) — there is **no** `app/service-areas/[slug]` route; individual suburb pages are flat pages served by `app/[slug]`.

### Site chrome & layout

`app/layout.tsx` (root) loads fonts, the site-wide JSON-LD `@graph` (business + WebSite, see SEO below), and wraps everything in `LazyMotionProvider` → `SiteChrome`. **`components/layout/site-chrome.tsx` is a client component that branches on `usePathname()`**: `/lp/*` routes get bare chrome (the landing layout supplies header/footer); every other route gets the full header, footer, smooth-scroll, scroll progress, and the welcome intro loader. Header nav links use `HoverPrefetchLink` (`components/ui/hover-prefetch-link.tsx`) — prefetch on hover/touch intent only, because the 9 always-in-viewport nav links otherwise fire ~1 MB of route prefetch at load; footer links are `prefetch={false}`. GA4 (gtag) loads via `components/analytics/deferred-analytics.tsx` on `requestIdleCallback`, not `afterInteractive`.

### SEO

> **Before creating or substantially editing any page, read [`on-page-seo.md`](on-page-seo.md) and satisfy every applicable item.** It is the canonical on-page-SEO checklist (15 categories / 80+ items) tailored to this repo's helpers + content pipeline, with a per-page-type required-schema matrix and a "definition of done". Every page-generation task starts there.

- `config/site.ts` — single source of truth for NAP (name/address/phone), nav, hours, social, URLs, legal entity (`legalName` — no invented corporate suffix; an audit flagged a bogus "LLC") and `abn` (TODO: fill with the real ABN — renders in the footer + schema `taxID` once set). **Hours in prose must use `formatHoursSummary()` (`lib/utils.ts`)**, never hand-written strings — the Contact page once showed a third conflicting hour set.
- **Review figures have ONE source: `getReviewsSummary()`** (CMS reviews). The site-wide schema `aggregateRating`, the hero's rating widget (passed as a prop from `app/page.tsx`), and `/reviews` all read it. Never hardcode a rating/count anywhere visible — schema-vs-visible divergence is a Google structured-data policy violation (the audit's #1 finding).
- `lib/seo/metadata.ts` — `buildMetadata({ title, description, path, image?, noIndex?, publishedTime?, lastModified? })` produces a `Metadata` object with canonical/OG/Twitter defaults. Use it for every page's `generateMetadata`. It applies `title.absolute` (the root `"%s | Capital Garage Doors"` template is **not** appended — author titles complete and ≤60 chars), emits the default 1200×630 OG card with dimensions+alt unless a page-specific `image` is passed, and `console.warn`s in dev when title >60 / description >160 chars.
- `lib/seo/schema.ts` — JSON-LD builders rendered via `components/seo/json-ld.tsx`. The site-wide entity is ONE `@graph` (`siteGraphSchema()` in `app/layout.tsx`): HomeAndConstructionBusiness (`@id` `…/#business`, GeoCircle areaServed, hasMap) + WebSite. Per-page nodes reference the business by `BUSINESS_ID` — never emit a second standalone Organization/LocalBusiness for the same entity.
- `app/sitemap.ts` (real `lastmod` on every URL — hubs inherit their newest child's date; no `changefreq`/`priority`, Google ignores them), `app/robots.ts`, `app/manifest.ts`, `app/llms.txt/route.ts` (AI-assistant site index per llmstxt.org, built from the data layer) are generated from the data layer + site config.
- Security headers (HSTS, nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy) + `poweredByHeader: false` are set in `next.config.ts` `headers()`. No CSP yet (needs an inline-script inventory first).
- **`scripts/sync-seo-fixes.ts`** — re-runnable CMS content-fix sync (titles ≤60, broken-link repoints, de-orphan links, pricing pins, hero-asset fixes). Defaults to the LOCAL CMS; run against production only with explicit `CMS_API_URL=https://cgd.runasp.net CMS_ADMIN_PASSWORD=…`. Gotcha it encodes: article `RelatedArticles` links are slug-ified and re-prefixed `/blog/` by `map-article.ts` — a non-blog URL in that group renders as a phantom link; use `RelatedServices` (pass-through hrefs) instead. `scripts/import-new-service-pages.ts` and `scripts/import-new-problem-pages.ts` are the same-pattern importers that created the roller-installation + sectional-doors service pages and the 7 problem pages WITH pricing/review pins attached (the bulk importer leaves pins empty). `scripts/import-door-type-pages.ts` (same pattern + an append-if-missing related-links step on existing pages) created the four door-type pages — `/roller-doors-perth`, `/tilt-garage-doors-perth`, `/custom-garage-doors-perth`, `/commercial-roller-doors-perth` — completing the type × segment matrix with the existing sectional + commercial-hub pages; their heroes live on the Bunny CDN under `capital-garage-door/door-types/`, re-uploadable via `npx tsx scripts/upload-door-type-images.ts` (which deliberately skips the one source render showing a competitor-branded shirt). `scripts/import-new-cost-guide-pages.ts` (same pattern) created the three cost-guide pages — `/garage-door-spring-replacement-cost-perth`, `/garage-door-service-cost-perth`, `/garage-door-motor-replacement-cost-perth` — with each cost-table row pinned to a `PricingItems` scenario (enriching the not-yet-enriched `includes/costFactors/nextStep` columns, mirroring `sync-seo-fixes.ts`) plus repair-page cross-links. Remember: `app/[slug]` now sets `dynamicParams = true` (on-demand rendering), so a page created in the CMS resolves on the live site **without** waiting for a deploy — it's only added to `generateStaticParams`/prerendered at the next build; `app/problems/[slug]` follows the same default.

### Icons

Content stores icons as **strings** (e.g. `"Wrench"`). `lib/icons.ts` maps the string to a Lucide component via `resolveIcon(name)` / `iconMap` (falls back to `Wrench`). When content references a new icon, add it to `iconMap` or it silently falls back. (`components/page/icons.ts` is a parallel map for the page-template section components.)

### UI primitives

`components/ui/*` are the low-level primitives (button, dialog, card, accordion, carousel, tabs, sheet, select, etc.). They are built on **Base UI (`@base-ui/react`), not Radix** — there is no `@radix-ui` dependency. When adding or wiring a primitive, import from `@base-ui/react/...` and follow the existing files. `cn()` (clsx + tailwind-merge) lives in `lib/utils.ts` and is the standard className combiner. Styling is **Tailwind v4** (`app/globals.css`, no `tailwind.config`); a few components use v4-only syntax like `mask-[...]` and arbitrary `bg-[size:...]`.

### Forms

There are **no local lead forms or server actions** anymore — the old `submitQuote` stub (`lib/actions/quote.ts`) and its form UIs were replaced by the live quote embed (see **Quote embed** above). `components/forms/*` are now thin wrappers around `QuoteFrame` with per-page prefill.

The business email is **never rendered as plaintext** (anti-spam-harvester): every "email us" surface uses `components/ui/obfuscated-email.tsx` (`ObfuscatedEmail`), which base64-decodes the address in `useEffect` so it exists only in the browser DOM, not the served HTML. `email` is deliberately omitted from all JSON-LD (`lib/seo/schema.ts`) for the same reason — keep the address out of `config/site.ts`-rendered output. If the email changes, update both `siteConfig.business.email` and the `ENCODED` constant in the component.

`framer-motion` is loaded lazily through `LazyMotionProvider`; GSAP + Lenis power the smooth-scroll and the garage-door intro/reveal animations. ### CMS (live — ASP.NET Core + SQL Server)

The CMS that `docs/cms-architecture.md` designed is **built and running**, not a draft. It's a separate ASP.NET Core (clean-architecture) backend in **its own repo** at `C:\Users\Mohammad swedan\source\repos\Capital Garage Door CMS\` (API project `CapitalGarageDoor.Cms.Api`), serving `http://localhost:5179` in dev (`CMS_API_URL` overrides). In Development it auto-applies EF migrations and seeds the admin account against SQL Server **LocalDB** on startup — run it with `dotnet run --project "CapitalGarageDoor.Cms.Api" --launch-profile http`. Its 8 anonymous public GETs are **output-cached server-side** (5-min TTL backstop; freshness is event-driven — every content mutation evicts the matching cache tags post-commit via `PostCommitCacheBehavior`, which also now fires the revalidation webhook AFTER the DB commit, evict-first/notify-second; kill switch `OutputCache__Enabled=false` + restart). A cached response carries an `Age` header; requests with an `Authorization` header always bypass the cache.

**Frontend integration (this repo):**
- `lib/cms/*` — the typed API client (`client.ts`), admin/auth (`admin.ts`), reviews (`reviews-client.ts`), DTO→type mappers (`map-*.ts`), editor serializers, and content importers.
- `app/admin/*` — the CMS admin dashboard + page editor, plus `app/admin/api/*` route handlers that proxy the backend. `app/api/revalidate` is the ISR webhook the backend calls on **every page mutation that changes the public site** — create-as-published, update (both hrefs on a slug rename), publish, unpublish, delete. The webhook revalidates the page path, expires the `cms-sitemap` + `cms-page:{routeGroup}:{slug}` fetch tags (`revalidateTag(tag, { expire: 0 })` — Next 16 two-arg form), and refreshes `/sitemap.xml`, `/image-sitemap.xml`, `/feed.xml`, and the route group's listing page(s) — so sitemap + listings track CMS adds/deletes within seconds. `app/robots.ts` advertises both sitemaps and deliberately does **not** disallow `/lp/*` (noindex must stay crawlable to be seen).
- `app/api/chat/route.ts` — same-origin proxy for the **Smart Garage Assistant**. Forwards conversations to the CMS `POST /api/assistant/chat` (DeepSeek LLM + RAG over CMS content) with the `ASSISTANT_PROXY_SECRET` shared secret (= backend `Assistant:ProxySecret`). The DeepSeek key is **CMS-side only** (`DeepSeek__ApiKey`); it is never in this repo or the client bundle. See the AI chat widget under *Interactive / conversion features*.
- **Media library**: every image is a backend `Asset` carrying an `AssetCategory` (enum; FE option list `components/admin/asset-categories.ts`). `/admin/media` (`components/admin/media/*`) browses the library by category, with search + pagination, and edits alt/category or deletes (in-use assets are protected by the backend). The editor's **Asset Picker** (`components/admin/editor/asset-picker.tsx`) and the classic forms' image field (`AssetUploadField` in `components/admin/fields.tsx`) both offer **pick-from-library or upload** — every upload lands in the categorised library (shared `components/admin/media/asset-upload-form.tsx`). Backend `AssetsController` does category/alt-text filtering on the paged list plus `PUT`/`DELETE /api/admin/assets/{id}` (mutations via `app/admin/asset-actions.ts`).
- **Public Gallery vs Media Library** — two *separate* things. The media library (above) is the reusable asset store; the **public gallery** (`/gallery`) is a curated showcase that *references* library assets but is its own `GalleryItem` collection with its own metadata: `Title`, `ServiceType` (free-text — the public "type" filter), `Suburb` (optional), `Caption` (description/body), `Category`, optional before-image, `SortOrder`. Managed at `/admin/gallery` (`components/admin/gallery-*`, `app/admin/gallery-actions.ts`; picks its main/before images from the library via the Asset Picker). The public page (`components/sections/gallery/gallery-filter-grid.tsx`) filters by **type + category + suburb** and **paginates client-side** over the full ISR list (options/counts derived from the items); it reads through `getGalleryItems()` → `cmsGallery()` (`GET /api/gallery`, behind `CMS_CATALOGS`) with a `content/gallery.ts` fallback. Backend `GalleryController` (`api/admin/gallery` CRUD); the `Title`/`ServiceType`/`Suburb` columns were added by the `AddGalleryItemMetadata` migration. **Bulk-rebuild the gallery from a folder of real job photos** with `npx tsx scripts/seed-gallery.ts` (compresses to WebP → uploads to the Bunny zone `capital-garage-door/gallery/` → wipes the existing items → registers assets by CDN URL + creates items incl. before/after pairs → revalidates `/gallery`; needs `CMS_ADMIN_PASSWORD` + `REVALIDATE_SECRET`, and `BUNNY_STORAGE_KEY` or the CMS `appsettings.json` on disk). - The `lib/data/*.ts` cutover seam is **active**: per-type flags (`CMS_SERVICE_PAGES`, `CMS_COMPARISON_PAGES`, …, `CMS_CATALOGS`, `CMS_REVIEWS`) decide whether each type reads from the CMS or falls back to local `content/*.ts`. They now **default ON in code** (`(process.env.CMS_… ?? "on") === "on"`), so a deploy with no env set (e.g. Netlify) reads from the CMS; set a flag to `"off"` to force that type back to local content. Likewise `CMS_API_URL` **defaults to the deployed backend `https://cgd.runasp.net`** — `.env.local` overrides it to `http://localhost:5179` for local dev. Because production is the default, `npm run build` in any environment (not just with a local CMS) reaches the live CMS unless overridden — see **Build/runtime dependency** below.

**Build/runtime dependency:** `app/[slug]` resolution (`lib/cms/client.ts` `cmsResolve()`) **throws** when the API is unreachable, so `npm run build` — which prerenders those pages — **requires the backend running**, or it fails at static generation with `ECONNREFUSED`. The strict `cmsSitemap()` used by `app/sitemap.ts` also throws on failure (deliberate: at runtime a failed regeneration keeps serving the last good sitemap instead of a 200 that silently dropped every CMS URL), while the lenient `cmsSitemapSafe()` behind every `get…Slugs()` returns `[]`. Catalog/review reads fall back gracefully (`try/catch → []`), so non-`[slug]` routes (incl. the home page) still render without it. For a backend-free type check, use `npx tsc --noEmit`. `docs/admin-dashboard-and-editor-plan.md` covers the admin/editor build.

### Deployment (production)

**`https://capitalgaragedoors.com.au` serves from the user's own VPS** (Ubuntu 24.04, srv833288) as the isolated Docker Compose stack **`capitalgd`** — since 2026-07-06; design + runbook in `docs/superpowers/{specs,plans}/2026-07-06-vps-frontend-deployment*.md`. **Pushing to `main` is a production deploy**: `.github/workflows/deploy.yml` SSHes to the VPS, hard-resets `/opt/capitalgd`, writes `.env` from GitHub repo secrets (`REVALIDATE_SECRET`, `ASSISTANT_PROXY_SECRET` — must equal the CMS production values; source of truth is the CMS repo's gitignored `appsettings.Production.json`), and runs `docker compose up -d --build`. The `Dockerfile` builds with `DOCKER_BUILD=1`, which gates `output: "standalone"` (+ a sharp tracing include) in `next.config.ts` so the Netlify build is untouched; the image build prerenders against the live CMS (a failed build leaves the old container serving). Topology: Cloudflare (proxied, SSL mode **Full**, Always Use HTTPS) → host nginx `:80`/`:443` (`/etc/nginx/sites-available/capitalgd.conf`, self-signed origin cert in `/etc/nginx/certs/`, `www`→apex 301, **no** `/api` split — this app's `/api/*` routes must reach the container) → `127.0.0.1:8082` → `capitalgd_frontend` (port 3000). The VPS hosts two other untouchable stacks (`ecampus`, `alzoubi`); this repo is public, so **no secrets or the origin IP in committed files**. **Netlify (cgdperth.netlify.app) still builds `main` as a warm standby** — rollback = revert the two Cloudflare A records for apex+`www` to Netlify's `75.2.60.5`, proxy OFF.

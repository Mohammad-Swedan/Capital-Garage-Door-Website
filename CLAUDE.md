## Architecture

This is a marketing/SEO site for a Perth garage-door business. Almost every page is **data-driven** — from local TypeScript content by default, or from the **live CMS** where its cutover flags are on (see **CMS** below) — rendered through a small set of reusable template components. Public pages are statically generated at build time (`generateStaticParams` + `dynamicParams = false`) with ISR revalidation; there is no per-request fetching for them (the CMS, when enabled, is read at build/revalidate, not per request). The `/admin/*` CMS dashboard is the exception — it is dynamic/server-rendered.

### The content pipeline (the core pattern)

Each page *type* flows through four layers — to add or change content you usually touch only the first:

1. **`content/<type>/...`** — the content store. Two shapes exist, both ending in a **registry** that exports an array:
   - **Directory-per-type** (one file per instance): `content/<type>/<slug>.ts` is a plain typed object; the sibling `content/<type>/index.ts` imports each instance and exports them as an array. Used by the larger page types — `articles`, `case-studies`, `comparison-pages`, `cost-guides`, `landing-pages`, `service-pages`.
   - **Single-file registry**: a flat `content/<type>.ts` exporting the array directly. Used for the smaller/list-style datasets — `services.ts`, `problems.ts`, `reviews.ts`, `testimonials.ts`, `gallery.ts`, `service-areas.ts`, `service-area-regions.ts`, `service-suburb-pages.ts`, `blog.ts`.
   - Ship a new page by adding the entry (and pushing onto the registry array) — no routing or component changes.
2. **`lib/data/<type>.ts`** — an `async` data-access layer (`get…BySlug`, `get…Slugs`, `get…`) wrapping the registry. There is one per content type (see `lib/data/` for the full list). **All call sites (routes, templates, sitemap) go through this layer, never the `content/` registries directly.** It is deliberately async so the backing store swaps from local files to the CMS API without changing call sites — a cutover that is **now live** behind per-type flags (see **CMS** below; original design in `docs/cms-architecture.md`).
3. **`types/<type>.ts`** — the interface shared by the content file, the data layer, and the template. `types/index.ts` holds the cross-cutting ones (`FAQ`, `Service`, `Problem`, `ServiceArea`, `BreadcrumbItem`).
4. **`components/.../<type>-page-template.tsx`** — the `…PageTemplate` component that consumes one typed object and renders the page from composable section components in `components/sections/<type>/` (or `components/page/` for the service-suburb template).

### Routing

Most routes are thin: resolve slug → call the data layer → render the template, plus `generateMetadata` using `buildMetadata`.

- **`app/[slug]/page.tsx` is shared by five "flat" page types** — brand, service, comparison, cost-guide, and service-suburb pages all live in one top-level slug namespace and are resolved by trying each registry in turn (in that order — **brands first**, because that registry is local and costs no network round-trip; the first match wins, so slugs must be unique across all five). `generateMetadata` and the default export each walk the same chain. **Never add a sibling `app/[other]/page.tsx`** — Next.js rejects two differently-named dynamic segments at the same path level (ambiguous-route build error). Add a new flat type by extending this file's resolution chain *and* its `generateStaticParams` `Set` — and keep `generateMetadata` and the default export in the same order (both walk the chain independently).
- Other types have their own namespaced dynamic routes: `app/blog/[slug]`, `app/case-studies/[slug]`, `app/problems/[slug]`, `app/lp/[slug]`.
- `app/lp/*` are **paid landing pages**: conversion-first, `noindex`, never linked in-site, and they use their own minimal chrome from `app/lp/layout.tsx`.
- **Static listing / standalone pages** (their own folder, no dynamic segment): `app/page.tsx` (home), and the index pages `app/services`, `app/service-areas`, `app/cost-guides` (now the price-list hub — see the sub-bullets below), `app/blog`, `app/case-studies`, `app/problems`, `app/reviews`, `app/gallery`. ### Site chrome & layout

`app/layout.tsx` (root) loads fonts, the site-wide JSON-LD `@graph` (business + WebSite, see SEO below), and wraps everything in `LazyMotionProvider` → `SiteChrome`. **`components/layout/site-chrome.tsx` is a client component that branches on `usePathname()`**: `/lp/*` routes get bare chrome (the landing layout supplies header/footer); every other route gets the full header, footer, smooth-scroll, scroll progress, and the welcome intro loader. Header nav links use `HoverPrefetchLink` (`components/ui/hover-prefetch-link.tsx`) — prefetch on hover/touch intent only, because the 9 always-in-viewport nav links otherwise fire ~1 MB of route prefetch at load; footer links are `prefetch={false}`. **The Services / Doors / Motors / More nav items are Base UI `NavigationMenu` mega-menus** (`components/layout/mega-menu.tsx`, content from `config/nav-menus.ts`; per-menu panel width via `PANEL_WIDTH`): the panel mounts only when it opens, so the brand logos never load at page load (LCP guard), and on mobile Services/Doors/Motors become accordion groups inside the full-screen menu. **Nav de-crowded 2026-09-01**: Gallery/Blog/About moved into the small "More" dropdown (+ Warranty, reviews footer link), "Price Calculator" renamed "Pricing" (since 2026-09-30 it links to the `/cost-guides` price-list hub, not `/calculator` — see **Smart price calculator**), Home shows at every lg+ width, and the Get Quote header button now shows from lg (was xl-only). On MOBILE the "More" links render FLAT (header.tsx special-cases `menu === "more"` — the dropdown exists only for desktop width); a "More" accordion would be a regression. Because both the panels and the mobile accordion are client-mounted, an `sr-only` "Site sections" `<nav>` at the top of the header server-renders every menu href (54 links at 2026-09-30, built by `navMenuHrefs()`) — without it the brand pages and `/garage-doors-perth` would have no crawlable site-wide inlink at all. ### Analytics & conversion tracking

**`lib/analytics.ts` `track(event, params)` is the only way this site emits an analytics event.** Added 2026-08-02, after a GA4 query found the property held *nothing but automatic events* (`page_view`, `session_start`, `scroll`, `first_visit`, `user_engagement`) — no call, quote, booking, chat or calculator signal existed, so there was no way to answer "which pages produce leads?".

`track()` pushes **both** shapes on purpose:
- `dataLayer.push({ event, ...params })` — a plain object, which is what **Google Tag Manager** reads. `gtag.js` ignores plain objects. **The GTM container `GTM-PLPC3F3L` is live (2026-08-08)**: `DeferredGoogleTagManager` in `components/analytics/deferred-analytics.tsx` loads it the same deferred, production-only way as gtag (the `<noscript>` iframe half is server-rendered in `app/layout.tsx`), so these pushes now feed GTM triggers directly. (Ads is the intended consumer.)
- `gtag("event", …)` pushed as an `arguments` object — which is what actually delivers to **GA4, via gtag.js directly, NOT through GTM**. **Never add a GA4 configuration/Google-tag to the GTM container** — GA4 delivery already happens through gtag.js, and a second GA4 tag in GTM would double-count every page view and event. If GA4 is ever migrated into GTM, remove `DeferredGoogleAnalytics` in the same change.

**This dual push is the whole point.** The pre-existing `trackChatEvent` did only the first, so every chat CTA event it fired for months was silently discarded. It now delegates to `track()`.

Its 8 anonymous public GETs are **output-cached server-side** (5-min TTL backstop; freshness is event-driven — every content mutation evicts the matching cache tags post-commit via `PostCommitCacheBehavior`, which also now fires the revalidation webhook AFTER the DB commit, evict-first/notify-second; kill switch `OutputCache__Enabled=false` + restart). A cached response carries an `Age` header; requests with an `Authorization` header always bypass the cache.

**Frontend integration (this repo):**
- `lib/cms/*` — the typed API client (`client.ts`), admin/auth (`admin.ts`), reviews (`reviews-client.ts`), DTO→type mappers (`map-*.ts`), editor serializers, and content importers.
- `app/admin/*` — the CMS admin dashboard + page editor, plus `app/admin/api/*` route handlers that proxy the backend. `app/api/revalidate` is the ISR webhook the backend calls on **every page mutation that changes the public site** — create-as-published, update (both hrefs on a slug rename), publish, unpublish, delete. The webhook revalidates the page path, expires the `cms-sitemap` + `cms-page:{routeGroup}:{slug}` fetch tags (`revalidateTag(tag, { expire: 0 })` — Next 16 two-arg form), and refreshes `/sitemap.xml`, `/image-sitemap.xml`, `/feed.xml`, and the route group's listing page(s) — so sitemap + listings track CMS adds/deletes within seconds. `app/robots.ts` advertises both sitemaps and deliberately does **not** disallow `/lp/*` (noindex must stay crawlable to be seen).
- `app/api/chat/route.ts` — same-origin proxy for the **Smart Garage Assistant**. Forwards conversations to the CMS `POST /api/assistant/chat` (DeepSeek LLM + RAG over CMS content) with the `ASSISTANT_PROXY_SECRET` shared secret (= backend `Assistant:ProxySecret`). The DeepSeek key is **CMS-side only** (`DeepSeek__ApiKey`); it is never in this repo or the client bundle. See the AI chat widget under *Interactive / conversion features*.
- **Media library**: every image is a backend `Asset` carrying an `AssetCategory` (enum; FE option list `components/admin/asset-categories.ts`). `/admin/media` (`components/admin/media/*`) browses the library by category, with search + pagination, and edits alt/category or deletes (in-use assets are protected by the backend). The editor's **Asset Picker** (`components/admin/editor/asset-picker.tsx`) and the classic forms' image field (`AssetUploadField` in `components/admin/fields.tsx`) both offer **pick-from-library or upload** — every upload lands in the categorised library (shared `components/admin/media/asset-upload-form.tsx`). Backend `AssetsController` does category/alt-text filtering on the paged list plus `PUT`/`DELETE /api/admin/assets/{id}` (mutations via `app/admin/asset-actions.ts`).
- **Public Gallery vs Media Library** — two *separate* things. The media library (above) is the reusable asset store; the **public gallery** (`/gallery`) is a curated showcase that *references* library assets but is its own `GalleryItem` collection with its own metadata: `Title`, `ServiceType` (free-text — the public "type" filter), `Suburb` (optional), `Caption` (description/body), `Category`, optional before-image, `SortOrder`. Managed at `/admin/gallery` (`components/admin/gallery-*`, `app/admin/gallery-actions.ts`; picks its main/before images from the library via the Asset Picker). The public page (`components/sections/gallery/gallery-filter-grid.tsx`) filters by **type + category + suburb** and **paginates client-side** over the full ISR list (options/counts derived from the items); it reads through `getGalleryItems()` → `cmsGallery()` (`GET /api/gallery`, behind `CMS_CATALOGS`) with a `content/gallery.ts` fallback. Backend `GalleryController` (`api/admin/gallery` CRUD); the `Title`/`ServiceType`/`Suburb` columns were added by the `AddGalleryItemMetadata` migration. **Bulk-rebuild the gallery from a folder of real job photos** with `npx tsx scripts/seed-gallery.ts` (compresses to WebP → uploads to the Bunny zone `capital-garage-door/gallery/` → wipes the existing items → registers assets by CDN URL + creates items incl. before/after pairs → revalidates `/gallery`; needs `CMS_ADMIN_PASSWORD` + `REVALIDATE_SECRET`, and `BUNNY_STORAGE_KEY` or the CMS `appsettings.json` on disk). Its `MANIFEST` (per-photo SEO title/alt/caption/category) is the single source of truth and is re-exported to regenerate the `content/gallery.ts` fallback. To **ADD** photos without wiping the existing gallery, use `npx tsx scripts/add-gallery-images.ts` instead — same pipeline minus the delete loop, with a `suburb` field on each manifest entry (suburb-rich local-SEO metadata) and `sortOrder` continuing above the current max; it appends to `content/gallery.ts` rather than regenerating it. (Its July-2026 run added 20 suburb-tagged repair/roller/commercial/motor/before-after items — items 19–38.) **Gallery images MUST resolve to `jadara-hub.b-cdn.net`** (the only external host in `next.config.ts` `remotePatterns`) — a `GalleryItem` whose `Asset.CdnUrl` is on `localhost:5179` or `cgd.runasp.net` renders broken via `next/image` on the public page. `next/image` also carries a `title` attr on the gallery card + service/article/page heroes for image SEO; the image sitemap (`app/image-sitemap.xml`) additionally lists the home page's static images.
- The `lib/data/*.ts` cutover seam is **active**: per-type flags (`CMS_SERVICE_PAGES`, `CMS_COMPARISON_PAGES`, …, `CMS_CATALOGS`, `CMS_REVIEWS`) decide whether each type reads from the CMS or falls back to local `content/*.ts`. They now **default ON in code** (`(process.env.CMS_… ?? "on") === "on"`), so a deploy with no env set (e.g. Netlify) reads from the CMS; set a flag to `"off"` to force that type back to local content. Likewise `CMS_API_URL` **defaults to the deployed backend `https://cgd.runasp.net`** — `.env.local` overrides it to `http://localhost:5179` for local dev. Because production is the default, `npm run build` in any environment (not just with a local CMS) reaches the live CMS unless overridden — see **Build/runtime dependency** below.

**Build/runtime dependency:** `app/[slug]` resolution (`lib/cms/client.ts` `cmsResolve()`) **throws** when the API is unreachable, so `npm run build` — which prerenders those pages — **requires the backend running**, or it fails at static generation with `ECONNREFUSED`. The strict `cmsSitemap()` used by `app/sitemap.ts` also throws on failure (deliberate: at runtime a failed regeneration keeps serving the last good sitemap instead of a 200 that silently dropped every CMS URL), while the lenient `cmsSitemapSafe()` behind every `get…Slugs()` returns `[]`. Catalog/review reads fall back gracefully (`try/catch → []`), so non-`[slug]` routes (incl. the home page) still render without it. For a backend-free type check, use `npx tsc --noEmit`. `docs/admin-dashboard-and-editor-plan.md` covers the admin/editor build.

### Deployment (production)

**`https://capitalgaragedoors.com.au` serves from the user's own VPS** (Ubuntu 24.04, srv833288) as the isolated Docker Compose stack **`capitalgd`** — since 2026-07-06; design + runbook in `docs/superpowers/{specs,plans}/2026-07-06-vps-frontend-deployment*.md`. **Pushing to `main` is a production deploy**: `.github/workflows/deploy.yml` SSHes to the VPS, hard-resets `/opt/capitalgd`, writes `.env` from GitHub repo secrets (`REVALIDATE_SECRET`, `ASSISTANT_PROXY_SECRET` — must equal the CMS production values; source of truth is the CMS repo's gitignored `appsettings.Production.json`), and runs `docker compose up -d --build`. The `Dockerfile` builds with `DOCKER_BUILD=1`, which gates `output: "standalone"` (+ a sharp tracing include) in `next.config.ts` so the Netlify build is untouched; the image build prerenders against the live CMS (a failed build leaves the old container serving). Topology: Cloudflare (proxied, SSL mode **Full**, Always Use HTTPS) → host nginx `:80`/`:443` (`/etc/nginx/sites-available/capitalgd.conf`, self-signed origin cert in `/etc/nginx/certs/`, `www`→apex 301, **no** `/api` split — this app's `/api/*` routes must reach the container) → `127.0.0.1:8082` → `capitalgd_frontend` (port 3000). The VPS hosts two other untouchable stacks (`ecampus`, `alzoubi`); this repo is public, so **no secrets or the origin IP in committed files**. **Netlify (cgdperth.netlify.app) still builds `main` as a warm standby** — rollback = revert the two Cloudflare A records for apex+`www` to Netlify's `75.2.60.5`, proxy OFF. **`.github/workflows/ci.yml` is a build check that never deploys**: on pushes to `seo/**`, `feat/**` and `fix/**` branches and on pull requests to `main` it runs `npx tsc --noEmit`, the `node:test` suites, the offline brand guard and a production `next build` (which prerenders against the live CMS), with a read-only `contents: read` token. It is the build gate for feature branches when a local `next build` is impractical; `deploy.yml` (push to `main`) remains the only production path.
